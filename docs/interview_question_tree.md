# ERP Ops Copilot 面试追问树

## 1. 为什么做这个项目？

目标不是做一个只会读PDF的问答机器人，而是模拟 ERP 上线后的三类真实支持任务：规则查询、业务数据查询、异常定位，再加实施阶段常见的 UAT 辅助。

### 追问：为什么不让 LLM 自己写 SQL？

因为作品集场景更重视可控和可审计。模型生成任意 SQL 会带来误查询、越权甚至写操作风险，所以只开放参数化白名单 Tool。模型/Router只能选择 Tool 和实体，不能执行任意SQL。

## 2. Router 为什么先于 RAG？

PO/SO/SKU 的业务事实存在数据库里，RAG 文档不能回答“当前库存多少”这类动态事实。先路由可以把规则问题送知识库，把数据问题送 SQL，把诊断问题做“事实+规则”组合。

### 追问：Router错了怎么办？

当前本地版用透明规则并返回 `route_trace`，便于定位；Dify版会用 Question Classifier，但仍保留明确标签和回归 Case。高风险数据操作不由 Router 直接执行写操作，本项目只有只读查询。

## 3. RAG 怎么做？

本地版把知识库 Markdown 按二级标题切成 Chunk，用轻量 TF-IDF-like 余弦检索，并加入少量可检查的 ERP 同义词扩展。它不是生产级语义 Embedding，项目明确披露这一边界。

### 追问：为什么还做本地RAG？

为了让项目无 Key 也能完整运行、自动测试和复现；Dify 部署时再把 Knowledge Retrieval 换成平台向量检索。

## 4. PO100怎么诊断？

SQL 查询采购单、明细和供应商后得到采购5件、累计验收3件、剩余2件，状态为 PARTIAL_RECEIVED。规则检查确认 0<received<ordered，因此解释为部分验收，并建议后续到货继续引用原PO且不得超量。

## 5. SO100怎么诊断？

订单需求5件，SQL查询当前库存3件，因此 stock_sufficient=false，决策为 BLOCK，缺口2件。系统建议先补货至少2件或调整订单数量，不执行任何库存写入。

## 6. UAT为什么不用LLM直接生成？

本地核心版先用确定性规则模板，确保关键边界必然覆盖，例如累计超量、零数量、重复提交和事务回滚。Dify版可以让LLM改善表达，但不能丢掉这些必测控制点。

## 7. 你怎么验证项目？

分三层：单元/端到端自动化测试、固定合成功能/RAG回归、最后单独封存一份开发后才执行的合成 Holdout 集。所有指标都明确不是生产准确率，也不代表真实企业用户效果。

## 8. 如果接真实 SAP 怎么改？

不改业务层的“路由—工具—证据—诊断”原则，但数据层不再直连模拟 SQLite；会通过企业批准的 API/OData/RFC/中间层读取授权数据，增加身份鉴权、字段脱敏、日志审计、环境隔离和变更管理。写操作需要审批和更严格的权限，不会让LLM直接执行。
